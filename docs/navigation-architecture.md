# 네비게이션 아키텍처

카메라·IMU 수집은 그대로 두고, **지도 통합 → 동적 요소 → 네비게이션 알고리즘**을
한 구조로 정리한다. 기준 코드: Rubik `31eacc7`의 관측 데이터, Map의 `app/map/gird.py`
격자, PR #1의 경로 엔진(`app/graph`, `app/profile`, `app/routing`, `app/schedule`).

## 1. 전체 구조

```text
[수집 · Rubik]
L0  관측 레코드 (2초 창: 위치, 노면, 경사, 진동, objects) → Supabase
─────────────────────────────────────────────────────────────
[지도 구축 · Map 저장소, 일괄 처리]
L1  세션 정리     주행 단위로 묶기, 진행 방향, 품질 필터
L2  지도 매칭     관측 → 간선 + 간선 위 위치
L3  간선 상태     방향별 경사 프로필, 노면, 진동, 경사 구간 분할
L4  동적 이벤트   후보 → 확인 → 활성 → 만료
─────────────────────────────────────────────────────────────
[해석 · 경로]
L5  프로필 해석   통행 가능 여부 + 비용 (기존 엔진 확장)
L6  경로 탐색     A*, 대안 경로, 선택 이유
─────────────────────────────────────────────────────────────
[네비게이션 · 실시간]
L7  위치 추적, 경로 이탈 감지, 안내 생성, 재탐색
```

**원칙:** 연결 구조(graph)와 측정 속성(간선 상태)과 시간 변동(이벤트)을 따로
저장한다. 모델이나 집계 방식이 바뀌어도 graph는 그대로 두고 L3·L4만 다시 계산한다.

## 2. 지도 정보 통합

### 정보 출처와 역할

| 출처 | 담당 | 갱신 |
|---|---|---|
| OpenStreetMap | 배경 지도만 | 고정 |
| 실험 구역 graph (GeoJSON, 직접 그림) | **연결 구조의 정답.** 계단, 출입구, 경사로 시설 | 현장 확인할 때 |
| 출입구 개방 시간 | 시간 규칙 | 학기마다 |
| Rubik 관측 | 경사, 노면, 진동 | 주행할 때마다 |
| 카메라 후보, 수동 입력 | 동적 이벤트 | 수 분~수 일 |
| 격자 (`gird.py`) | **화면 표시와 관측 밀도용.** 경로 계산에는 안 씀 | 주행할 때마다 |

### 값이 서로 다를 때 우선순위

```text
현장 확인(survey) > 실측, 2회 이상 주행 > 실측, 1회(잠정) > 카메라 추정 > 미측정
```

속성마다 `값, 출처, 근거 수, 갱신 시각`을 함께 저장한다. 경로 화면에서
"이 경사는 3회 실측값"처럼 근거를 보여줄 수 있어야 한다.

### 간선 상태 (L3 출력)

```text
edge_state (간선 하나, from→to 방향 기준)
  정적:     length_m, stairs, curb_cm, ramp, entrance_id, width_level   ← graph에서
  실측:     slope_profile  [(offset_m, slope_pct, n), ...]   간선 위 위치별 경사
            slope_pct      대표값(중앙값)
            slope_max_pct  5m 이동창 최댓값
            slope_std, n_passes, surface(+비율), vibration_hz, last_observed
  상태:     status = surveyed | measured | provisional | unknown
```

- 반대 방향은 저장하지 않고 엔진이 부호를 뒤집는다(PR #1 `Graph.outgoing`).
- **경사 시작·끝 처리:** 경사 프로필에서 경사가 바뀌는 지점을 찾아 간선을 나눈다
  (노드 종류 `ramp_start` / `ramp_end`). 간선 하나 안에서는 경사가 고르고,
  "20m 앞 오르막" 안내의 기준점이 된다.

### 지도 매칭 (L2)

| 단계 | 방법 | 언제 |
|---|---|---|
| 1차 | 15m 안 후보 간선 중 거리와 진행 방향 차이(45° 이내)로 선택. 애매하면 미확정 | 토요일 데모 |
| 2차 | HMM(Viterbi): 관측 확률 = 거리(σ = max(GPS 정확도, 4m)), 전이 확률 = "경로상 거리 − 직선거리" 차이 | 이후 |

인도와 차도처럼 6m 간격 나란한 길은 최근접만으로 자주 틀린다. HMM은 앞뒤
관측의 연결성으로 바로잡는다.

## 3. 동적 요소

### 이벤트 구조

```text
event
  event_id, type, source (camera | manual | schedule)
  evidence: [obs_id ...]
  edge_id, offset_from_m, offset_to_m        ← 간선 위 구간
  first_seen, last_seen, expires_at
  confidence, status (candidate | confirmed | active | expired | cleared)
  effect (info | penalty | block), severity
```

### 종류별 기본값 (`config/events.json`)

| 종류 | 유효시간 | 확인 조건 | 경로 반영 |
|---|---|---|---|
| 이동 객체 (사람, 주행 차량) | 기록만 | - | 반영 안 함. 시간대 혼잡도 통계 |
| 정차·방치 (주차 차량, 킥보드) | 30분 | 2개 창 이상 + 같은 위치 | 비용 가중 |
| 임시 설치물 (바리케이드, 라바콘) | 1일 | 다른 주행 재관측 또는 수동 확인 | 가중 또는 차단 |
| 공사·통제 (수동 입력) | 입력 기간 | 입력 즉시 | 차단 |
| 출입구 운영 시간 | 일정표 | 규칙 | 시간 밖이면 차단 |

### 따로 고안할 문제 4가지

1. **객체 위치 추정:** 카메라가 앞을 보므로 객체를 관측 지점이 아니라 진행 방향
   앞 3~15m 구간에 붙인다(데모). 개선안은 카메라 높이+IMU 기울기로 지면 거리 추정.
2. **부재 관측·커버리지:** 이벤트 조기 해제를 위해 "봤는데 없었다"를 알아야 한다.
   추론 성공 창이 덮은 간선 구간을 커버리지로 기록. 카메라 꺼진 구간은 부재로 안 침.
3. **확인 규칙:** 한 주행 내 다중 관측과 다른 주행 재관측은 신뢰도가 다르다.
   `confidence`를 근거 수와 서로 다른 주행 수로 계산.
4. **프로필별 반영 강도:** 같은 정차 차량도 보행자엔 무시, 휠체어엔 큰 가중.
   이벤트 효과에 프로필별 계수.

**이번 주 범위:** 수동 이벤트의 생성·만료·재탐색까지. 카메라 후보는 표시만.
→ 구현과 확정 규칙: [route-choice-and-events.md](route-choice-and-events.md).
종류 설정은 `config/events.json`(공사·통제, 임시 설치물, 정차 차량·킥보드, 혼잡)이고,
이벤트는 간선 전체에 양방향으로 적용한다.

## 4. 네비게이션 알고리즘

### 비용 식 (기존 엔진 확장)

지금 엔진은 경사를 절댓값·선형으로만 처리하고 프리셋의 `w_slope`가 전부 0이다.
오르막과 내리막을 따로 다룬다.

```text
cost(arc) = L/100 × [ w_distance
                    + w_up   × (g⁺ / g_ref)²        오르막
                    + w_down × (g⁻ / g_ref)²        내리막 (휠체어엔 내리막도 부담)
                    + w_surface × 노면 페널티 + w_vib × 진동 페널티
                    + w_unknown × 미측정 비율 ]
            + 지점 페널티(계단·문턱) + 이벤트 페널티
통행 불가: 계단(프로필), g⁺ > max_up, g⁻ > max_down, 차단 이벤트, 운영 시간 밖
```

- `Profile`에 `w_up`, `w_down`, `max_up_pct`, `max_down_pct` 추가. 기존 `w_slope`,
  `max_slope_deg`는 호환용으로 남긴다(값이 지정되면 상·하한을 거기서 파생).
- 휠체어 한도 결정도 여기서 함께.

### 탐색

| 기능 | 방법 |
|---|---|
| 기본 | 지금은 다익스트라. A*는 나중(휴리스틱 = 직선거리/100 × w_distance, 비용 하한이라 최적 보장) |
| 출발·도착 | 현재 GPS를 가장 가까운 간선에 투영, 임시 노드 삽입 |
| 시간 의존 | 출입구 개방을 출발 시각이 아니라 그 간선 도착 예상 시각으로 판단(보행 1.2, 휠체어 0.9 m/s) |
| 대안 | 추천(프로필 최적) + 최단(거리만) 항상 계산. 추가 대안은 "쓴 간선 ×1.5 후 재탐색", 최대 3개, 추천보다 30% 넘게 비싸거나 80% 넘게 겹치면 버림 |
| 선택 이유 | 요약값 차이로 설명. "60m 더 걸음 · 오르막 15.0% 1곳 회피 · 경사 미측정 40m 포함" |
| 불확실성 | 미측정 거리 표시. 신중 모드는 미측정 경사를 주변 최댓값으로 가정 |

### 실시간 안내 루프 (L7)

```text
입력: 폰 GPS(1Hz), 경로 선, 안내 지점 목록
매 위치마다:
  1. 경로 선 투영 → 진행률 (10m 이상 뒤로 튀면 무시)
  2. 이탈: 경로까지 거리 > max(15m, 2×GPS 정확도)가 2회 연속 → 재탐색
  3. 안내: 30° 이상 분기 회전, 경사 20m 전 "오르막 7%, 15m", 노면 변화, 앞 이벤트
  4. 이벤트 확인(30초): 남은 경로에 차단 → 재탐색. 가중 이벤트는 새 비용 10%+
     개선 시만 교체(경로 떨림 방지) → app/nav/reroute.py check_reroute()
  5. 도착: 목적지 10m 안
```

**데모: 기록 재생 네비게이션.** 녹화된 주행 GPS를 1초씩 흘려 넣으면 안내·이탈·
재탐색이 동작한다. 데모와 자동 테스트 양쪽에 쓴다.
